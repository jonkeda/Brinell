# Known Shorthand Doc Types

This document lists shorthand names I already understand well and what I will produce when you ask for each one.

## Requirements and Scope

### GAP - Gap Analysis
A Gap Analysis request creates a document comparing current state versus target state. It identifies missing capabilities, process or technology gaps, priorities, and an action roadmap to close them.

### BRD - Business Requirements Document
A BRD request creates a Business Requirements Document focused on business outcomes and stakeholder needs. It emphasizes business objectives, process impact, high-level requirements, assumptions, dependencies, and approval criteria.

### PRD - Product Requirements Document
A PRD request creates a Product Requirements Document that defines what should be built and why. It normally captures goals, user personas, user stories, scope, constraints, success metrics, and release boundaries.

### FRD - Functional Requirements Document
An FRD request creates a Functional Requirements Document that specifies system behavior in detail. It often includes functional rules, inputs and outputs, user flows, edge cases, and traceable requirement statements.

### NFR - Non-Functional Requirements
An NFR request creates a Non-Functional Requirements document defining quality constraints around the solution. It covers performance, security, reliability, availability, maintainability, usability, and compliance expectations.

### TRD - Technical Requirements Document
A TRD request creates a Technical Requirements Document describing technical constraints and implementation needs. It usually includes architecture constraints, interfaces, data requirements, technology choices, and operational considerations.

### RFC - Request for Comments
An RFC request creates a Request for Comments style proposal intended for review and feedback. It commonly includes problem statement, goals and non-goals, proposed design, alternatives, risks, rollout plan, and open questions.

### CR - Change Request
A Change Request request creates a formal proposal to modify system behavior, process, or scope. It generally includes justification, impact assessment, risks, approval workflow, implementation plan, and rollback notes.

## Architecture and Technical Design

### HLD - High-Level Design
An HLD request creates a High-Level Design that describes the system structure at component level. It generally includes major modules, interaction boundaries, data flow, integration points, and key architectural decisions.

### LLD - Low-Level Design
An LLD request creates a Low-Level Design with implementation-level details for developers. It typically includes class or module breakdown, method responsibilities, data structures, validation logic, and sequence details.

### API SPEC - API Specification
An API Spec request creates a contract document for service endpoints and integration behavior. It usually defines resources, request and response schema, status codes, auth model, validation rules, and example payloads.

### ADR - Architecture Decision Record
An ADR request creates an Architecture Decision Record documenting one specific decision and its context. It usually includes status, decision drivers, options considered, chosen option, consequences, and trade-offs.

## Roadmaps and Development Planning

### ROADMAP - Product or Delivery Roadmap
A ROADMAP request creates a time-ordered or milestone-based plan across multiple phases. It usually includes major goals, sequencing, dependencies, milestones, and expected outcomes over time.

### PHASE - Phase Document
A PHASE request creates one document dedicated to a single phase of work. It typically includes the phase goal, scope, deliverables, dependencies, risks, and completion criteria.

### PLAN - Execution Plan
A PLAN request creates a concrete action plan for a phase, feature, or workstream. It usually includes sequenced work items, assumptions, blockers, checkpoints, and validation steps.

### STEPDOC - Step Document
A STEPDOC request creates a small, focused implementation document for one step within a phase or plan. It typically includes the objective, tasks, dependencies, and validation for that step.

### MILESTONE - Milestone Document
A MILESTONE request creates a planning document centered on a major delivery checkpoint. It usually includes milestone goals, entry and exit criteria, dependencies, and readiness measures.

### EPIC - Epic Definition
An EPIC request creates a planning document for a large body of work that spans multiple stories or steps but is smaller than a full roadmap. It usually includes scope, desired outcomes, constraints, and the main workstreams.

### WORKSTREAM - Workstream Document
A WORKSTREAM request creates a planning document for one parallel track of work within a phase or larger effort. It typically includes goals, ownership, dependencies, and deliverables for that track.

### TASKMAP - Task Breakdown Map
A TASKMAP request creates a structured breakdown of work into tasks and subtasks. It usually includes hierarchy, sequencing, and dependencies so the execution path is clear.

### IMPLEMENTATION - Implementation Document
An IMPLEMENTATION request creates a development-focused execution document with technical detail. It typically includes technical scope, design notes, coding tasks, validation, and rollout considerations.

### CHECKLIST - Delivery Checklist
A CHECKLIST request creates a compact, actionable list for delivery or readiness work. It usually includes ordered check items with clear completion signals.

## Planning and Risk

### RISK - Risk Assessment
A Risk Assessment request creates a structured evaluation of threats and uncertainties tied to a change or project. It records risk likelihood, impact, mitigation, contingency, owner, and monitoring approach.

## Testing and Validation

### TESTPLAN - Test Plan
A Test Plan request creates a testing strategy document for a feature or release. It typically includes scope, test types, environments, tooling, entry and exit criteria, responsibilities, and risk-based priorities.

### RTM - Requirements Traceability Matrix
An RTM request creates a Requirements Traceability Matrix connecting requirements to validation artifacts. It maps each requirement to design, implementation, and tests so coverage and gaps are visible.

### TC - Test Cases
A Test Cases request creates detailed, executable test scenarios. It usually includes preconditions, steps, test data, expected results, pass or fail criteria, and traceability to requirements.

### UAT - User Acceptance Testing
A UAT request creates a User Acceptance Testing document focused on business-user validation. It typically includes scope, acceptance criteria, test scenarios, expected outcomes, and a sign-off section so stakeholders can confirm the feature is ready.

## Operations and Release

### DEP - Deployment Plan
A Deployment Plan request creates a release execution document for moving changes into target environments. It includes sequencing, prerequisites, ownership, verification checkpoints, communication plan, and contingency actions.

### ROLLBACK - Rollback Plan
A Rollback Plan request creates a controlled recovery plan to revert a deployment safely. It describes rollback triggers, exact reversal steps, data safety checks, validation steps, and stakeholder notifications.

### RELEASE-NOTES - Release Notes
A Release Notes request creates a user-facing summary of delivered changes in a release. It usually includes new features, fixes, known issues, upgrade notes, and any required user actions.

### RUNBOOK - Operations Runbook
A Runbook request creates an operations execution guide for support or on-call use. It typically includes symptom checks, diagnostic commands, branching troubleshooting steps, recovery actions, and escalation paths.

### SOP - Standard Operating Procedure
An SOP request creates a Standard Operating Procedure for repeatable operations. It provides step-by-step instructions, prerequisites, responsibilities, decision points, and quality or safety checks.

### KB - Knowledge Base Article
A KB request creates a Knowledge Base article for quick reference and self-service support. It usually includes issue description, common causes, resolution steps, known limitations, and related links.

## Incident and Improvement

### RCA - Root Cause Analysis
An RCA request creates a Root Cause Analysis document that explains what failed, why it failed, and how to prevent recurrence. It usually includes timeline, impact, causal chain, contributing factors, corrective actions, and preventive follow-ups.

### PIR - Post-Incident Review
A PIR request creates a Post-Incident Review document focused on incident handling and organizational improvement. It includes what happened, what worked, what failed, communication quality, and remediation tracking.

### POSTMORTEM - Incident Postmortem
A Postmortem request creates a retrospective incident analysis document. It generally captures incident summary, impact, timeline, root causes, response effectiveness, lessons learned, and action items.

### CAPA - Corrective and Preventive Action
A CAPA request creates a Corrective and Preventive Action plan. It identifies immediate fixes for current issues and systemic controls that reduce recurrence, with owners, due dates, and verification steps.

### AAR - After Action Review
An AAR request creates an After Action Review focused on outcomes versus intent. It usually documents expected results, actual results, key deviations, lessons learned, and recommended next actions.

### RETRO - Retrospective
A Retrospective request creates a team improvement report based on completed work. It summarizes what went well, what did not, root themes, and concrete improvement actions with accountable owners.
