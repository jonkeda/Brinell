# SQL replay: a database stand-in recorded from the real one

A proposal, 2026-10-25; revised the same day after an architecture review (major revision).
`Brinell.Mocking` stands in for an HTTP backend with WireMock. Nothing like it exists for a
database: SQL Server's wire protocol (TDS) has no maintained fake, and `sqlmock`-style libraries
need every query and its rows written by hand. This proposes recording what a test sends to the
real database and what comes back, then replaying it with no database. The scope is Brinell and
its samples; trying it on an app comes later.

## Outcome

It ships in two parts, and the first is useful alone.

- **The log.** Every command a test sends, with its parameters, timing and result size, kept per
  test. It answers questions with no fidelity risk: how many queries, an N+1, an unexpected
  query, a SQL snapshot to approve. It also measures how much time the database takes, and so
  whether replay is worth having.
- **Replay.** A test recorded once against the real database runs again with the database never
  opened. A command that doesn't match fails the test loudly, naming the command; nothing falls
  through to the database.

Replay proves the app sends the same commands as when it was recorded. It doesn't prove the
database still accepts them, so a suite that replays still runs against the real database at its
gate.

Three risks decide whether replay works, and the spike tries to disprove each before anything is
built: matching under timing-dependent traffic, values generated by the app that later queries
depend on, and EF Core's SQL Server provider expecting a real `SqlConnection`.

## Where it sits

A provider-neutral core with two thin adapters.

| Part | What it does |
| --- | --- |
| Core | The exchange model, the matcher, value binding, the store; knows no provider |
| ADO.NET adapter | Wraps a `DbConnection`, for raw ADO.NET and Dapper |
| EF Core adapter | Interceptors: `ConnectionOpening` suppressed in replay, `ReaderExecuting` and friends answered with `SuppressWithResult` |
| Provider rules | Value normalization and type handling, one typed rule set per provider (SQLite, SqlClient) |

The EF adapter exists because a wrapped connection breaks EF Core on SQL Server: its type mappings
read spatial and `hierarchyid` columns through `SqlDataReader`-only methods, its retry logic reads
`SqlException.Number`, and parts of it build their own `SqlConnection`. With interceptors EF keeps
its real connection and never opens it.

The app's seam for the ADO.NET adapter is `DbDataSource` (.NET 7 and later), the framework's own,
rather than a factory of Brinell's. An app that already opens connections through a data source
changes nothing; the Todo sample moves to one.

## The exchange and the recording

An exchange is one call: a command (reader, non-query, scalar), a transaction mark (begin,
commit, rollback), or an error. Each recording keeps two files, because a recording is both an
assertion and a fixture:

- **The command log** (`<test>.sql.md`): the commands as readable SQL with their parameters, in
  the order they ran. It's the part a reviewer reads, like an approval snapshot.
- **The results** (`<test>.results.json`): each command's result sets (column name, CLR type,
  provider type name, values), rows affected, output parameters, or the error.

Values are kept in a canonical form: `decimal` as a string so its scale survives, `DateTime` with
its kind, `DateTimeOffset` with its offset, binary and provider-specific values as base64 with a
type name. Collation and the schema table are not recorded.

Each recording carries a stamp: a hash of the migrations, the provider's version and the EF
version. When the stamp doesn't match, the run reports "stale: re-record" before any miss.

## Matching: occurrences between write barriers

A command's key is its normalized text and normalized parameters. A replayed command gets the
result recorded for the same key and the same occurrence: the second identical `SELECT` gets the
second recorded result.

- **Writes are barriers.** Writes must come in their recorded order. The reads between two writes
  are a set, matched in any order, so Blazor's double render at prerendering and components that
  load in parallel don't miss.
- **State follows from occurrences.** The `SELECT` after an `INSERT` is a later occurrence, so it
  gets the later rows; a rollback needs nothing special.
- **Concurrent writes.** Two writes that race, where their order changes later results, are
  detected at recording (they overlap in time) and reported; that test stays on the database.
- **A miss.** The failure lists the nearest recorded command beside the actual one, with the part
  that differed.

## Value binding

Ignoring a volatile value is not enough: a GUID made at an insert comes back in `WHERE Id = @p0`
and in later result rows. So volatile values are bound, not ignored.

- The first time a recorded volatile value meets a live one, the two are bound.
- Every later occurrence of either must agree with the binding, and recorded results are rewritten
  through the binding table on the way back.
- **Volatile values are found by recording twice.** Values that differ between two clean runs of
  the same test are marked volatile in the recording; nobody configures GUIDs, clocks and identity
  values by hand. A rule can still be added in code.
- The guide says the cheapest fix is at the source: `TimeProvider` and injectable id generation.

## Parameter normalization

The provider rules compare values, not representations:

| Case | Rule |
| --- | --- |
| `null`, `DBNull.Value` | Equal |
| `short`, `int`, `long`, enums | Compared as an integer value |
| `decimal` | By value, not scale |
| `DateTime` | By ticks; a different kind is a warning |
| `DateTimeOffset` | By instant (`UtcTicks`) |
| `Size`, `Precision`, `DbType` | Ignored by default |
| Parameter names | By position after normalizing, as EF renames them |
| JSON parameters (EF's `Contains`) | Parsed and compared as JSON |

The rules are typed C# with their own tests, never a JSON configuration.

## Errors and what is refused

Errors are exchanges. A recorded error replays as the provider's own exception where the rules
know how to build one (`SqlException` by reflection, `SqliteException` by its constructor), so
`catch (SqlException e) when (e.Number == 2627)` still runs. Where they can't, the test is marked
as needing the database rather than replaying a different exception type.

Refused with a named exception: bulk copy, `SqlDependency` and query notifications, `GetSchema`,
and provider-only reader methods outside the EF adapter.

## Which test a command belongs to

In a UI test the browser drives the server, and the test's `AsyncLocal` doesn't flow into request
threads, SignalR circuits or hosted services. Two options, chosen by the fixture:

- **A host per test** (or per test collection run one at a time): every command the host sends
  belongs to the current test.
- **A test id at the boundary:** the browser context sends a header, a middleware puts the
  test's scope on the request and the circuit. Hosted services stay unscoped and are refused in
  replay unless their commands are part of a shared startup recording.

Startup traffic (migrations, seeding, reference data) is recorded once per stamp and shared, not
copied into every recording.

## Recording maintenance

Recordings go stale faster than HTTP cassettes: SQL is an implementation detail refactored weekly,
and one added column changes every query that loads its entity. So:

- **Re-recording is by hand**, never on a miss.
- **A re-record prints a summary:** commands added, removed and changed, and rows changed per
  command, rather than a JSON diff. The summary is written beside the recording.
- **A check fails** when a results file changed without its command log or summary changing, so a
  re-record can't slip through unread.
- **The stamp** turns "everything misses after a migration" into one clear message.

## Never in scope

Synthesizing results for a command that wasn't recorded (that road ends in a database emulator),
recordings shared across providers, re-recording by itself, and TDS on a socket.

## Steps

0. **Spike, to disprove the risks.** A small Blazor Server app with EF Core on a local SQL Server
   in `samples/` (one page that reads, one that writes, a spatial column, a unique key):
   - **Measure first.** The database's share of the Todo suites' time, from the speed plan's
     timing spans. If it is small, replay waits and only the log is built.
   - **EF on SQL Server** through interceptors: the page's scenarios replayed, including the
     spatial column and a unique-key `SqlException` caught by its number.
   - **Timing-dependent traffic.** One Blazor scenario, prerendering on, replayed 20 times in a
     row: zero misses with occurrence keys and write barriers.
   - **Churn.** The spike app's scenarios recorded, then 10 typical changes made as commits (a
     column added, an `Include`, a renamed property, an EF minor upgrade, a new filter). Counted:
     misses per change, recordings touched, and whether the stamp and summary made each one clear.
   The spike passes when all four hold; otherwise the proposal changes before step 1.
1. **The log.** `Brinell.Mocking.Data` with the ADO.NET and EF adapters in record-only mode; the
   command log per test, counts, an N+1 check and a SQL snapshot assertion. The Todo sample moves
   to `DbDataSource` and its suites write logs.
2. **Replay core.** Occurrence keys, write barriers, the provider rules for SQLite and SqlClient,
   errors, the stamp, the miss message.
3. **Value binding.** Binding and rewriting, and volatile values found by recording twice.
4. **Test scoping.** A host per test and the test-id header, with the shared startup recording.
5. **Maintenance.** The re-record summary and the check on unread re-records.
6. **Todo's suites on replay**, measured against their SQLite runs, and the spike app's suite on
   replay against SQL Server.
7. **Guide and decision.** `docs/guides/sql-replay.md` and an AD on when a test replays and when
   it needs the database.

## Open questions, with proposals

- **One package or two?** Proposal: one, `Brinell.Mocking.Data`, with EF Core as a dependency of
  a second, `Brinell.Mocking.Data.EntityFrameworkCore`, so raw ADO.NET users don't pull in EF.
  Under AD-026 the dependency split is the reason it earns its place.
- **One recording per test, or per scenario and head?** Proposal: per test, named by the xUnit
  test as the call log is. A scenario on two heads sends the same commands and shares it.
- **Should the spike app stay as a sample?** Proposal: yes, if the spike passes; Brinell has no
  sample with EF Core and SQL Server, and steps 1 to 6 need one.
- **Should replay be released at all if the log shows the database is a small share of test
  time?** Proposal: no; ship the log, keep replay on the shelf with the spike's numbers.
