## The shape of it

A UAT workspace is **a project and a fixture**. Everything else is derived from
those two, chosen in the toolbar for the session, or owned by the fixture.

```markdown
## Runtime

| Field   | Value                             |
| ---     | ---                               |
| Project | ./Brinell.Samples.Todo.Uat.csproj |
| Fixture | TodoUatFixture                    |
```

That is the whole config for the Todo workspace, replacing ten rows of which
three are currently wrong. Presenter gains an editor for those two rows, a
fixture picker, a Build button, and Debug/Release and platform switches that
never touch the file.

### Why so little

Three findings from the archived notes, each measured:

1. **`Controls` and `Commands` are never loaded.** Only `Pages` reaches
   `LoadRequired`; the other two contribute probe directories and validation
   errors about files nothing opens.
2. **`AppPath` is read by nobody.** Presenter exports it to `APPIUM_APP_PATH`,
   `WPF_APP_PATH` and friends; no driver, factory or fixture reads any of them.
   Only `STRIDE_APP_PATH` is read, as the middle of a three-way fallback. The
   fixture owns the app: `GetDefaultAppPath` is **abstract** on every fixture
   base, and `TodoAppFixtureBase` already resolves per platform, Debug before
   Release, matched to the TFM.
3. **Paths rot; names and projects do not.** Both checked-in configs that spell
   out a path are stale — `win10-x64` in Todo's `AppPath`, `net10.0-windows7.0`
   in `Brinell.Maui.Uat.Tests`. The six that use bare assembly names are all
   correct.

`AppPath` survives in the grammar as an optional override, for Stride and for an
app with no project. It stops being required, and stops being validated as an
error.

## Resolution

### The Pages assembly

`dotnet msbuild <project> -p:TargetFramework=<tfm> -p:Configuration=<config> -getProperty:TargetPath`,
spawned, evaluation-only. Measured at **~0.5 s**, cold or warm, with no build and
no restore — and it works on a project that has never been built, returning where
the output *will* go.

Rules the measurements dictate:

- **Always pass `TargetFramework`** when the project multi-targets, or
  `TargetPath` comes back **empty, silently**. Read `TargetFrameworks` in the
  same call to know.
- **Pass at least two `-getProperty` names**: one prints a bare value, several
  print JSON.
- **Cache** per (project, TFM, configuration), invalidated on the project's write
  time. Resolution is async; 0.5 s is fine on demand and wrong per keystroke.
- **A clean evaluation says nothing about buildability.** Evaluation never runs
  the workload check, so a project needing an uninstalled workload resolves fine
  and then fails `NETSDK1147` at build. Show the build's own error verbatim.
- Spawn, do not host MSBuild in-process. In-process was measured at ~215 ms per
  repeat against ~550 ms for a spawn — not worth `Microsoft.Build` in a MAUI app
  and an `MSBuildLocator` ordering constraint at startup.

### Target, and the fixture

Both come from one reflection-only pass over the built Pages assembly with
`MetadataLoadContext` — **46 ms**, no side effects, and the lock is released on
dispose:

```text
AutoGeneratedProgram   (no base)
TodoUatCollection      (no base)
TodoUatFixture         → TodoAppFixture → TodoAppFixtureBase → MauiTestFixtureBase [Brinell.Maui]   ✓ [TestModuleScan]
```

- **Fixture candidates** are ranked by whether they derive from a Brinell fixture
  base, annotated with `[TestModuleScan]`, and filtered to non-abstract types
  with a parameterless constructor — which is Presenter's own instantiation rule
  ([UatExecutionService.cs:191](../../../srcnew/Brinell.Presenter/Services/UatExecutionService.cs#L191)),
  stated in Presenter's own words instead of discovered by failure.
- **Target** falls out of the root base: `MauiTestFixtureBase` → MAUI,
  `WpfTestFixtureBase` → WPF, `WinFormsTestFixtureBase` → WINFORMS,
  `StrideTestFixtureBase` → STRIDE. A config declaring `Target | WPF` over a MAUI
  base becomes a contradiction Presenter detects.

**`Target` leaves the config entirely.** It is derivable, and a derived value
cannot disagree with itself.

That is not free — it changes the xUnit side, where seven test classes declare it:

```csharp
protected override UatRuntimeValidationOptions RuntimeValidation { get; } =
    new(Target: "MAUI", Fixture: "TodoUatFixture");
```

`UatRuntime.Validate` today compares that string against `config.Runtime["Target"]`
and throws when it is missing. It should compare it against **the target derived
from the fixture** instead — and the runtime is handed the live fixture instance
(`new UatRuntime(fixture, configPath)`), so it can walk `fixture.GetType()`'s base
chain directly, with no `MetadataLoadContext` and no config lookup.

This makes the check stronger, not weaker. Today it verifies that one string in a
file matches another string in a test class; neither has any connection to what
the fixture actually is. After the change it verifies the *fixture* is what the
test class claims.

The declarations in `RuntimeValidation` stay exactly as they are. What changes is
what they are checked against. A config row remains accepted as an override for a
fixture that derives from no Brinell base.

Four other readers move to the derived value:
`UatTargetRegistry.GetRequired`, `UatWorkspaceConfigInspector`,
`UatWorkspaceService`'s summary line, and the `["target"]` metadata at
[UatScenarioTestBase.cs:287](../../../srcnew/Brinell.Uat/UatScenarioTestBase.cs#L287).

Its only remaining runtime job is deciding whether to place the AUT window beside
Presenter.

### The name search stays, demoted

The ranked tree walk in `UatWorkspaceConfigInspector` and
`UatRuntimeAssemblyResolver` keeps working for bare names and stale paths, with
two changes:

- **Labelled.** Every resolution carries its route — *configured*, *evaluated*,
  *derived*, *found by search* — and the editor shows that word. Silent fallback
  is how `net10.0-windows7.0` lived in a checked-in config unnoticed.
- **Scoped.** Project folder, then workspace, then probe directories, then the
  tree — and never above `FindSolutionRoot`, whatever `WorkingDirectory` says. A
  miss costs ~1 s under `Brinell/` and ~4 s under the container repo, and it runs
  from the `AssemblyLoadContext.Resolving` handler.

## The editor

The Config tab becomes editable in place. It is already where you land when a
workspace fails to load, and the Presenter must stay narrow enough to sit beside
the app under test — so no modal wizard, and labels above fields at quarter
width.

```markui
+--- Brinell Presenter --------------------------------------+
| [Open][v] [Reload] [Validate]                      [Theme] |
| +--- Run ------------------------------------------------+ |
| | [Run] [Stop] [Next]  Delay <250_> ms                   | |
| | [Debug v] [windows v] [#1 Build]                       | |
| +--------------------------------------------------------+ |
| +--[Tree]--[[Config]]--[Diagnostics]--[Discovery]--[Cmd]--+ |
| | uat.config.md                        * unsaved         | |
| |                                                        | |
| | Project  <./Brinell.Samples.Todo.Uat.csproj> [#2 ...]  | |
| |                                                        | |
| | Fixture  [TodoUatFixture           v] [#3 Rescan]      | |
| |            derives MauiTestFixtureBase, scans pages    | |
| |                                                        | |
| | v Derived                                              | |
| |   Target   MAUI            from fixture base           | |
| |   Pages    …/net10.0-windows/…Uat.dll    evaluated  ok | |
| |   App      owned by the fixture                        | |
| |                                      [#4 Pin a value]  | |
| |                                                        | |
| | [#5 Save] [#6 Revert]        [#7 Open in editor]       | |
| +--------------------------------------------------------+ |
+------------------------------------------------------------+
```

**One editable path**, the project. Browse picks a `.csproj`, not a `.dll` buried
under `bin/Debug/<tfm>/<rid>/`.

**The fixture picker is the main event.** It lists candidates from the current
Pages assembly with the reason unusable ones are unusable — "abstract", "no
parameterless constructor" — rather than hiding them, because *"there are no
fixtures here"* and *"the fixtures here are all abstract"* are different problems.
When the assembly is missing it says **not built**, names the project, and offers
**Build**.

**Derived values are shown, never edited**, each with its route and a **Pin**
action that writes the current value into the file as an override. Derivation you
cannot see is worse than a path you must maintain.

**The toolbar carries the session choices**, because a configuration and a
platform are things you switch while demoing, not properties of the suite:

- `Debug` / `Release` — builds and loads *the tests*. The fixture picks the app's
  configuration itself, Debug first; say so in the UI.
- Platform — sets `APPIUM_PLATFORM` (`windows`, `android`, `ios`), the existing
  mechanism read by `BrinellMauiConfiguration`, after which the fixture resolves
  the matching binary. The picker offers only what the fixture declares (below).
  Android additionally shows disabled with its reason: `UatTargetRegistry` has no
  Android entry and AUT placement is Windows-only.
- **Build**, with a progress log, cancellation, and MSBuild's error text verbatim.

Both session choices persist per workspace in `PresenterUserSettings`, beside
`LastOpenedFolder`.

### A fixture declares its platforms — as an attribute, not a property

`TodoAppFixtureBase` throws `NotSupportedException` for anything but Windows and
Android. The picker should know that before offering iOS.

It has to be an **attribute**, because the picker runs *before* the assembly is
loaded, and reflection-only metadata cannot execute code. Measured on the real
assembly:

```text
TodoUatFixture: TestModuleScanAttribute(…Pages.TodoListPage) { NamespacePrefix=…Pages }   ✓ readable
  property read: FAILS (InvalidOperationException)
```

Constructor arguments and named arguments both come back; a virtual property
returns nothing until something is loaded and constructed — which is exactly what
the picker is trying to avoid.

So:

```csharp
[UatPlatforms(MauiPlatform.Windows, MauiPlatform.Android)]
public sealed class TodoUatFixture : TodoAppFixture
```

Absent, every platform the target supports is offered and the fixture's own
`NotSupportedException` remains the error — which is a good one. The attribute
turns a runtime throw into a disabled menu item, and it sits next to
`[TestModuleScan]`, which the same 46 ms pass already reads.

### State

| State | Header | Save | Run |
| --- | --- | --- | --- |
| Clean | `uat.config.md` | disabled | normal |
| Dirty | `* unsaved` | enabled | prompts to save |
| Invalid | `n problems` | **enabled** | blocked, as today |

Save stays enabled while invalid — half-fixing and saving is legitimate, and
refusing to write is how an editor loses work.

**Save reloads the workspace.** The point of editing the config is to make the
workspace work, so leaving Presenter showing the pre-save state is a half-step
that invites a manual Reload every time.

The cost is the reason this was ever in question: reload rebuilds the tree, which
today collapses it and drops the selection. So reload must **preserve tree state**
— expanded nodes by path, and the selected node by path, reapplied after the
rebuild, falling back to the nearest surviving ancestor when a node is gone. That
is worth having on the Reload button too, and it is a prerequisite for this
decision rather than a nicety: a Save that silently throws away where you were is
worse than no automatic reload.

When the config is still invalid, Save writes and reports; it does not reload,
because there is nothing to reload into.

Validation runs on every change,
through the same `UatWorkspaceConfigInspector.Inspect` the Diagnostics tab uses,
against the in-memory config: `Inspect` gains an overload taking a `UatConfig`,
and the existing signature becomes a wrapper. Never a second implementation.

Diagnostics gain a section and field name so the editor can place them; the flat
list Diagnostics renders becomes a projection of the same records.

**External change**: hold the modification time read at load. On Save, if it
moved, offer **Keep mine** / **Reload theirs**. No merge attempt. **Open in
editor** actively encourages this case.

### Startup, with no config

Pick the UAT project → Presenter derives the target, resolves the Pages assembly,
offers **Build**, then lists fixtures and asks you to choose one. Two decisions,
both from a list, and **Create** writes the two-row file.

It does not guess the fixture. A wrong guess that looks authoritative costs more
than a picker with one obvious answer in it.

## Writing the file

No config writer exists today — `UatConfigParser` is read-only. The writer belongs
beside it in `Brinell.Uat`, not in Presenter, because a headless `--init` will
want it too.

```csharp
public static class UatConfigWriter
{
    public static string Apply(string markdown, UatConfigEdit edit);
    public static string Create(UatConfigTemplate template);
}
```

Preservation rules, in priority order:

1. Unknown sections and prose survive untouched.
2. Unchanged rows are not rewritten — padding and alignment are per-row
   properties of the existing text.
3. A changed row keeps its position and its neighbours' column widths, so a save
   is a one-line diff.
4. A new row appends to its section; a new section appends in the parser's
   canonical order.
5. A removed row leaves no blank line.
6. Line endings and trailing newline follow the file as found.
7. A field at its default stays absent; the editor shows the default as
   placeholder text.

Acceptance: `Parse(Apply(md, edit))` equals the edit, **and**
`Apply(md, noOp)` is byte-identical, for every config in the repo. The second
property is the cheap one and the one that keeps configs hand-editable. Save
writes through a temporary file and replaces.

## Loading, and why Build needs it

A loaded assembly locks its file. Measured:

```text
before load               → writable YES
LoadFromAssemblyPath(dll) → loaded
after load                → writable NO (file in use)
```

`UatExecutionService` loads the Pages assembly into `AssemblyLoadContext.Default`,
which is **not collectible**, so that lock lasts the life of the process:

1. Open workspace, **Build** → works.
2. Run a scenario → assembly loaded and locked.
3. Edit a page object, **Build** → **fails**.
4. Restart Presenter.

Two consequences for this design:

- **Fixture listing never uses the running load path.** `MetadataLoadContext`
  releases its lock on dispose, so build → list → build again works.
- **Running moves to a collectible `AssemblyLoadContext` per session**, disposed
  when the session ends. This also fixes a standing hazard: today a workspace
  built against a different `Brinell.Maui` silently gets Presenter's, because
  everything shares one context.

The collectible context is the risky part. The fixture and every page object must
not outlive it, and `UatRuntimeAssemblyResolver` currently hooks
`AssemblyLoadContext.Default.Resolving`.

**A Build button must not ship before this lands.** One that works exactly once,
until you have run something, is worse than none.

No-op incremental builds, for sizing the progress UI: **6.5 s** for
`Brinell.Samples.Todo.Uat`, **9.1 s** for the MAUI sample app on Windows.

### Building the app

Out of scope for the config, still needed by the person. The convention
`Brinell.Wpf.Uat.Tests` already uses covers it:

```xml
<ProjectReference Include="..\..\samples\Brinell.Samples.Wpf.App\Brinell.Samples.Wpf.App.csproj"
                  ReferenceOutputAssembly="false" />
```

"Build it, don't reference it." One build produces both, MSBuild decides what is
up to date, and **Presenter never learns the app's path** — the build graph
carries it, the fixture finds the output. `Brinell.Presenter.Uat.Tests` does the
same with an explicit `<MSBuild>` task. The Todo, Maui and WinForms UAT projects
have no such reference; adding one is a project-file change, not a config change.

## Tests

Presenter is driven by its own UAT suite, so every control needs an `AutomationId`
and a page-object member from the start — no test may reach for the driver.

| Control | AutomationId |
| --- | --- |
| Project field / browse | `ConfigProjectInput` / `ConfigProjectBrowseButton` |
| Fixture picker / rescan | `ConfigFixturePicker` / `ConfigFixtureRescanButton` |
| Fixture candidates | `ConfigFixtureCandidateList`, items `ConfigFixtureCandidate{Index}` |
| Derived rows | `ConfigDerivedTarget`, `ConfigDerivedPages`, `ConfigDerivedApp` |
| Pin | `ConfigPin{Field}Button` |
| Save / Revert | `ConfigSaveButton` / `ConfigRevertButton` |
| Create | `ConfigCreateButton` |
| Per-field diagnostic | `ConfigDiagnostic{Section}{Field}` |
| Header state | `ConfigStateLabel` |
| Configuration / platform / build | `BuildConfigurationPicker` / `PlatformPicker` / `BuildButton` |
| Build log | `BuildLogText` |

Every control type already exists in `Brinell.Maui`: `Entry`, `Picker`,
`CheckBox`, `Button`, `Label`, `CollectionView`. Nothing to generate.

Collapsible sections put a real `Button` in the `Expander` header — the toolkit
Expander publishes no ExpandCollapse or Invoke pattern on Windows, so without it
the panel is unreachable from UI Automation (the WP3 "Route A" rule already in
`PresenterPage.xaml`).

**Unit tests** (`Brinell.Uat.Tests`): writer round-trip and byte-identity over
every config in the repo; preservation of unknown sections, prose, CRLF, ragged
columns; defaults not written.

**Scenarios** (`Brinell.Presenter.Uat.Tests`):

- `choose-fixture.uat.md` — open the Todo workspace, see the fixture flagged, pick
  `TodoUatFixture` from the list, save, run. The acceptance test for the whole
  design: a newcomer fixes that workspace without leaving Presenter.
- `create-missing-config.uat.md` — empty folder, pick a project, Create.
- `build-and-rescan.uat.md` — unbuilt workspace, Build, fixtures appear.
- `external-change-conflict.uat.md` — dirty editor, file changes on disk, both
  branches.

## Decisions taken

| Question | Decision |
| --- | --- |
| Does Save imply Reload? | **Yes** — and reload must preserve tree expansion and selection, which becomes a prerequisite rather than a nicety |
| Should `Target` stay in the file? | **No** — derived from the fixture base; `UatRuntime.Validate` compares `RuntimeValidation` against the live fixture instead of a config string |
| Can a fixture declare its platforms? | **Yes**, as `[UatPlatforms(…)]` — an attribute, because the picker reads metadata before anything is loaded |
| Prototype the collectible ALC first? | **Yes** — before slice 8, not during it |
| A raw-Markdown view in the editor? | **No** |

## Still to prototype

**Collectible ALC with a MAUI page-object graph.** Slice 10 is built and proven
on a minimal fixture: the Pages assembly is mapped during a session and writable
again once it is disposed, which a test asserts in both directions. Two things
had to change for that — the session drops its own object graph before the
context unloads, and the unload is followed by a collection — and neither is
enough on its own.

A real MAUI run now exercises it — the Presenter's own UAT suite runs a MAUI
workspace through a session — but nothing yet asserts that the *unload* completes
after one. What the first real run did expose is the other half of the problem:
the session context must let the **host** resolve every dependency it can, not
just the ones already loaded. Probing instead searched the tree by file name and
found an Android build of a dependency, which failed at run time with a missing
`libSystem.Native` and named neither the assembly nor the platform it came from.

Still worth doing: assert the release after a MAUI run, and keep "run the session
in a separate process" as the fallback if statics in FlaUI, Appium or the MAUI
handlers turn out to pin the context.
