# Phase 11 — Polish & Extensibility

## Goal

Final polish: settings UI, prompt customization, corpus sharing, and plugin architecture for future platform support.

## Tasks

### 11.1 — Settings: Dual-model selection, corpus configuration

Provide a settings page/dialog where the user configures LLM models and corpus behavior.

**Implementation details:**

- Add a **Settings** window (or a tab in an existing settings area) with:

  **LLM Models:**
  - **Analyzer model:** `ComboBox` bound to available models. This is the cheaper model used for pattern detection and analysis (e.g., `GPT-5.4`, `claude-haiku`). Used in Phase 5 analysis passes.
  - **Generator model:** `ComboBox` bound to available models. This is the smarter model used for code generation (e.g., `Claude Opus 4.6`, `gpt-4o`). Used for page object and custom control generation.
  - **Temperature:** `Slider` with range 0.0–1.0, step 0.05, default 0.2. Applies to both models (or separate sliders if needed).
  - **Max tokens:** `NumericUpDown` with range 1024–16384, default 4096. Per-model if the models have different limits.
  - **Timeout:** Optional field for LLM request timeout in seconds (default 120).

  **Corpus Settings:**
  - **Storage path:** `TextBox` + browse button for the root corpus storage directory (default: `%APPDATA%\Brinell.Scraper\corpora`).
  - **Auto-analyze after recording:** `CheckBox` (default: on). When enabled, automatically triggers analysis after recording stops (see Phase 8.4).
  - **Keep snapshot history:** `CheckBox` (default: on). When enabled, retains all snapshot versions; when off, only the latest snapshot per page is kept.

  **Per-site settings:** Each site also has its own namespace, output path, and URL aliases configured in the Site Settings dialog.

- Settings are persisted in a user-scoped settings file:
  - Location: `%APPDATA%\Brinell.Scraper\settings.json` or alongside the app in `appsettings.user.json`.
  - Use `System.Text.Json` for serialization.
  - Settings file is created with defaults on first launch if it doesn't exist.
- A `ScraperSettings` class holds all values, registered in DI as `IOptions<ScraperSettings>`.
- Changes take effect immediately (no app restart required) — use `IOptionsMonitor<T>` for live reload.
- Validation: temperature must be 0.0–1.0, max tokens must be positive integer within model limits, storage path must be a valid directory.

### 11.2 — Prompt customization: skill-based prompts with user additions

Allow the user to view and extend the LLM prompt. The base prompt is now delivered via the `brinell-conventions` SKILL.md file, not a monolithic prompt string. User additions are appended to the skill content.

**Implementation details:**

- The base Brinell conventions (PageObject naming, property patterns, using directives, etc.) live in `brinell-conventions/SKILL.md` and are loaded automatically into LLM sessions.
- UI: A multi-line `TextBox` showing the user's custom additions (not the full skill content — that's managed as a file).
- The user can:
  - **Append custom rules** (e.g., "Always use `data-testid` for element identification", "Prefix all control properties with `Ux`").
  - **Reset to default** via a button that restores the SKILL.md content to the built-in version.
- User additions are stored **per-site** — different sites may need different instructions (e.g., one site uses `data-testid`, another uses `aria-label`).
- At runtime, the final prompt = skill content + user additions + resolved variables.
- Prompt templates can use variables like `{{PageUrl}}`, `{{ElementCount}}`, `{{TargetNamespace}}` that are substituted at generation time.
- Include a **Preview** button that shows the fully resolved prompt: skill content + user additions + resolved variables for the current page/snapshot.
- Per-site additions are stored in the corpus SQLite database alongside other site configuration.

### 11.3 — Control type mapping overrides (fallback)

Manual control type mappings serve as a **fallback and override** mechanism. The primary control discovery is via the analysis pass (Phase 5), where the LLM proposes custom controls based on detected patterns. Manual mappings override the LLM's decisions when the user disagrees or needs deterministic behavior.

**Implementation details:**

- UI: A data grid or list editor where each row defines a mapping rule:
  - **Selector/Pattern** (string): CSS selector, tag name, or attribute pattern (e.g., `div.btn`, `[role="button"]`, `input[type="date"]`).
  - **Brinell Control Type** (ComboBox): Target control type from Brinell.Html (e.g., `ButtonControl`, `TextInputControl`, `SelectControl`, `CheckboxControl`). Also includes any custom controls generated by the analysis pass.
  - **Priority** (int): Higher priority rules are applied first when multiple rules match. Manual mappings take priority over LLM-proposed mappings by default.
  - **Notes** (optional string): User documentation for the rule.
- Rules are stored per-site in the corpus database (not a standalone JSON file):
  - Exported alongside the corpus in 11.4.
  - Migrated from the old standalone `control-mappings.json` if present.
- Rules are injected into the LLM prompt as explicit instructions: "When you encounter an element matching `div.btn`, treat it as a `ButtonControl`."
- Rules are also used post-generation to validate/correct the LLM's output — if the LLM ignores a mapping, a warning is shown.
- Provide **Add**, **Edit**, **Delete**, **Move Up/Down** buttons for rule management.
- Include a set of built-in default mappings (e.g., `<a>` → `LinkControl`, `<select>` → `SelectControl`) that the user can override but not delete.

### 11.4 — Export/import site corpus for team sharing

Enable exporting and importing entire site corpuses so team members can share captured data, analysis results, and generated controls without re-scraping.

**Implementation details:**

- **Corpus-level export (primary):**
  - Export an entire site corpus as a `.brinell-corpus` archive containing:
    - SQLite database (pages, snapshots, analysis results, pipeline state)
    - Site-specific SKILL.md files (`{site}-patterns/SKILL.md`, `{site}-controls/SKILL.md`)
    - Generated custom control source files
    - Control type mapping overrides
    - Per-site prompt additions
  - Export via **File → Export Corpus** or right-click on a site in the corpus panel.
  - File dialog defaults to `.brinell-corpus` extension.

- **Corpus-level import:**
  - **File → Import Corpus** opens a file dialog filtered to `.brinell-corpus` files.
  - On import, the corpus is restored with all associated data — snapshots, analysis, custom controls, mappings.
  - The user can then continue the pipeline (generate pages, re-analyze, etc.) without needing a live browser session.
  - If a site with the same name already exists, prompt: merge, replace, or import as copy.
  - Validate the archive format on import — show a clear error if the file is corrupt or from an incompatible version.

- **Individual snapshot export (secondary):**
  - Still supported for sharing a single page snapshot as `.brinell-snapshot` (JSON format).
  - Useful for bug reports or sharing a specific page structure.

- Archive format is versioned (`"formatVersion": 1`) to allow future schema changes with migration support.
- Consider supporting drag-and-drop of `.brinell-corpus` files onto the main window.

### 11.5 — Plugin architecture for non-HTML platforms

Define an extensibility model that allows Brinell.Scraper to support scraping from non-HTML platforms (e.g., WinForms, WPF, or MAUI apps via UIA).

**Implementation details:**

- Define an `IScraperPlugin` interface with corpus awareness:
  ```csharp
  public interface IScraperPlugin
  {
      string PlatformName { get; }
      Task<DomSnapshot> CaptureAsync(CaptureContext context);
      IReadOnlyList<ControlTypeMapping> GetDefaultControlMappings();
      string GetPromptInstructions();
      bool CanHandle(ScraperTarget target);
  }
  ```
  - `CaptureAsync` returns a `DomSnapshot` (the corpus-aware capture model from Phase 4) instead of raw elements.
  - `GetPromptInstructions()` returns platform-specific prompt additions that are appended to the skill content.
  - `CanHandle` determines whether this plugin handles the given target (URL, process, window handle, etc.).

- **HTML plugin** (built-in, default): Uses WebView2 + JavaScript DOM capture. This is the existing implementation refactored behind the interface.

- **Future: UIA plugin**: Uses FlaUI to capture the UIA automation tree from a running desktop application. Maps UIA `ControlType` values to Brinell control types. Target: `Brinell.WinForms`, `Brinell.Wpf`, `Brinell.Maui` page/control objects.

- **Plugin discovery:**
  - Assemblies in a `plugins/` directory next to the app are scanned for `IScraperPlugin` implementations.
  - Alternatively, plugins are registered in `appsettings.json` under a `"plugins"` array.
  - Built-in plugins are always available and don't need discovery.

- **Plugin selection in UI:**
  - A `ComboBox` or toolbar toggle to select the active scraping platform.
  - The UI adapts to the selected plugin (e.g., HTML plugin shows URL bar + WebView2; UIA plugin shows process picker + live element tree).

- **Shared pipeline:** Regardless of plugin, the downstream pipeline (analysis, LLM generation, Roslyn compilation, code output) remains the same. The plugin only affects the capture and control-mapping stages. Captured data feeds into the corpus like any other recording.

- Keep the plugin interface minimal for v1 — resist adding extension points until there are concrete second-platform requirements.

### 11.6 — MCP Server Evaluation

Per the Copilot SDK research, evaluate extracting corpus query tools into an MCP (Model Context Protocol) server for cross-tool sharing.

**Implementation details:**

- **Benefit:** An MCP server would make corpus tools reusable across multiple SDK clients and shareable with the team. Any MCP-compatible client (VS Code Copilot, CLI agents, CI pipelines) could query the corpus.

- **Candidate tools for extraction:**
  - `search_corpus` — search pages/elements across the corpus by selector, text, or attribute.
  - `get_page_snapshot` — retrieve the latest (or specific version) snapshot for a page.
  - `find_similar_elements` — find elements across pages that match a pattern (for custom control detection).
  - `get_generated_controls` — list generated custom controls with their source and usage.

- **Decision criteria:**
  - Only build if multi-user or cross-tool sharing is concretely needed.
  - If the scraper is the sole consumer, keep as custom tools in the Copilot SDK session (simpler, no server lifecycle to manage).
  - If a second consumer emerges (e.g., a CI pipeline, a VS Code extension, or a teammate's agent), extract to MCP.

- **For now:** Keep as custom tools in the SDK session. Revisit when Phase 8 (Workflow Automation) is complete and usage patterns are clearer.

- **If extracting:**
  - MCP server runs as a local process alongside the scraper app.
  - Corpus SQLite is the shared data source (read-only access from MCP clients; writes only through the scraper app).
  - Use the standard MCP transport (stdio or SSE) for client communication.

## Acceptance Criteria

- [ ] Settings UI has separate analyzer model and generator model selectors.
- [ ] Corpus settings (storage path, auto-analyze, snapshot history) are configurable.
- [ ] Settings persist across app restarts.
- [ ] User can add per-site prompt additions that are appended to the `brinell-conventions` SKILL.md content.
- [ ] Reset-to-default restores the SKILL.md to the built-in version.
- [ ] Preview button shows: skill content + user additions + resolved variables.
- [ ] Control type mappings work as fallback/override to the analysis-proposed controls.
- [ ] Manual mapping rules can be added, edited, deleted, and reordered.
- [ ] Mapping rules are injected into the LLM prompt and validated post-generation.
- [ ] Entire site corpus can be exported as `.brinell-corpus` archive.
- [ ] Corpus import restores all data (snapshots, analysis, controls, mappings, prompt additions).
- [ ] Individual snapshot export still supported as secondary option.
- [ ] Import validates format and shows clear errors for invalid/incompatible files.
- [ ] `IScraperPlugin` interface is defined with corpus-aware `CaptureAsync` and the HTML scraper implements it.
- [ ] Plugin selection UI is present (even if only HTML plugin is available initially).
- [ ] MCP server evaluation is documented with decision criteria and candidate tools.
- [ ] All new UI elements follow existing WPF styling and MVVM patterns.

## Dependencies

- **Phase 4** (Corpus) — Corpus storage, site management, and snapshot history underpin settings and export/import.
- **Phase 5** (Analysis, Skills) — Skill-based prompts, analysis-driven control discovery, and the `brinell-conventions` SKILL.md.
- **Phase 3** (DOM Capture) — Capture must be refactored behind `IScraperPlugin` for plugin architecture.
- **Phase 6** (Code Generation) — Prompt construction must support skill content, user additions, and injected control mappings.
- **Phase 8** (Workflow Automation) — Pipeline orchestrator integrates with auto-analyze setting and corpus export.
- **Phase 9** (UI Shell) — Settings and prompt customization UI integrate into the existing WPF shell.
